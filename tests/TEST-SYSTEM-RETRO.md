# 自建测试体系整改建议（基于 OCR 全量审查的漏检复盘）

> 背景：自建测试套件（Oracle A 静态 378 项 + Oracle B 浏览器 326 项）全绿的情况下，
> 外部 OCR 全量代码审查（deepseek-flash，42 文件）仍发现 **24 处真缺陷**，其中 1 条 Critical
> （必现死循环）+ 8 条 High（含 4 个"游戏根本玩不了/不可获胜"级别）。全部确认属实并已修复。
> 本文档回答三个问题：漏了什么、为什么漏、怎么改。交付对象：负责自建测试体系的会话。

## 一、漏检缺陷的根因分类（24 处 → 5 类系统性盲区）

| 盲区 | 漏检缺陷 | 为什么现有体系抓不到 |
|---|---|---|
| **A. 生成器数学性质** | runner 负数答案死循环；balance 除法方程不可解；clockrush 分钟 0–145；trivia 多正确答案/题干 undefined；duel 负数减法 | 断言只验证"能运行、有唯一正确项"，从未验证**题面与答案的数学一致性**、**值域约束**、**干扰项属性互斥**。这是"测了运行"没"测正确" |
| **B. 深度游戏状态** | runner 死循环只在 level≥5 触发；clockrush 只在 hardMode≥1 触发；speedmath 罚时/双击、reaction 罚时、merge2048 胜局后输入、trivia 生命耗尽 | 交互测试全部停留在**默认状态的第一次操作**，没有状态机模型，升级/惩罚/终局路径零覆盖 |
| **C. JS↔CSS 视觉契约** | connect4 落子隐形（CSS 期望 `<i>` 子元素但 JS 从未创建）；dots 网格 5 轨道 vs 49 节点；typing `.shake` 类未定义 | 断言停在 class 添加层面（"落子有 p1 类"），从未做 **computed style / 几何互证**；CSS 与 JS 的结构契约无任何检查 |
| **D. 跨组件与泄漏** | 搜索框被游戏键盘监听劫持（空格打不出）；语言菜单监听器每次换语言累积；typing 监听器跨重建累积；stage 类名跨局残留 | 测试以单游戏为孤岛，没有**组件间交互矩阵**（游戏键盘 × 头部输入框 × 语言重建），没有"N 次重建后监听器数量不变"的不变量 |
| **E. 可玩性元性质** | angles 物理参数导致**任何目标都不可能命中**（游戏不可获胜） | 只有"扣扳机有反应"的断言，没有"游戏可获胜/可失败"的元 oracle。功能性修复（submit 已接）≠ 行为闭环（真实能命中） |

## 二、根因复盘（为什么体系 design 成这样）

1. **Oracle 来源错位**：多数断言的预期来自"读实现后确认行为"，不是来自规格推导。
   "runner 按左键后棋盘有变化"是实现的影子；规格级的断言应是"任何关卡生成的门恰好 3 个值、
   恰好 1 个等于答案、全部非负"。—— 违反"预期来自规格，不是实现"。
2. **断言强度被数量稀释**：704 项里交互类断言大多是**存在性断言**（元素存在/类已加/Δ发生），
   不是**状态等价断言**（到达了预期终态）或**性质断言**（对任意输入成立）。
   漏斗表里的"数量"指标制造了虚假信心。—— 违反"断言强度 > 覆盖率 > 数量"。
3. **同作者盲区**：代码和测试出自同一会话，对"除法题显示 x÷3=7"这类**自认为对**的逻辑，
   写测试时会顺着实现写断言。缺少真正独立的第三方 oracle（OCR 审查 8.9 秒发现了我们三轮自测
   没发现的东西，本质是新鲜视角，不是模型更强）。—— 违反"对偶 oracle 隔离"的精神。
4. **L2.5 执行型 oracle 缺位**：exhaustive 方法论里"声称的输出 vs 真实运行"本是代码教学站
   第一优先级；对游戏站的同构物是"**生成器声称出题可解 vs 实际数学一致性**"，完全没做。
5. **探索式测试缺位**：SBTM 宪章式自由探索（"把这游戏玩到通关""故意输""在搜索框里打字"）
   一次都没做过——脚本全按 happy path 走，而 Agent 天然倾向测看起来正常的路径。
6. **环境噪声无预案**：后台标签页 transition 节流造成 V6 假失败，靠临场诊断才排除；
   计算样式断言前未剥离 transition/animation。

## 三、整改项（按优先级，均给出落地位置）

### P0-1 生成器性质检验成为游戏站标配（对应盲区 A）
- 每个含随机生成的游戏暴露 `_test` 钩子（已落地：runner/balance/clockrush/trivia），
  性质断言最小集：
  - **可解性**：题面可从答案数学推出（balance 的"解析题面→验算"模式，见 vaccine-generators V2）；
  - **值域**：所有产出量落在规格区间（clockrush 分钟 0–59，duel 答案 > 0）；
  - **互斥性**：属性型题目的干扰项不得共享正确项属性（trivia 偶数题 4 选项恰 1 偶数）；
  - **终止性**：一切 while 生成循环必须有 guard 且性质检验覆盖全部分支（runner level 1–8 × 60 次）；
  - **题干卫生**：渲染文本非空、不含 "undefined"/裸 key。
- 已落地于 `tests/vaccine-generators.js`（9 项断言）；**待办**：把剩余 10 款生成器类游戏
  （speedmath/percent/sequence/fractions/coords/sudoku/minesweeper/whack/changeup/simon）补齐同规格钩子与性质。

### P0-2 交互断言强度升级：存在性 → 状态等价（对应根因 1/2）
- B-2 的每条交互断言重审一遍，把"有 Δ"升级为"到达预期终态"。反例：
  - connect4 旧断言 `$$('.c4-hole.p1').length>=2`（类存在）→ 新断言：棋盘至少 2 子 **且**
    `getComputedStyle(i).transform` 为 scale(1)（剥离 transition 后）；
  - trivia 旧断言"轮次推进"→ 新断言：新题题干非空且与字典一致。
- 落地位置：`tests/browser-sweep-2-interactions.js` 逐条升级（P1 工作量）。

### P0-3 状态机覆盖（对应盲区 B）
- 为每款游戏列出状态转移表（idle→playing→win/lose/level-up/penalty），
  要求每条转移至少一次被脚本穿越。重点补：
  - runner 打到 level 5–8（可用 `_test` 钩子直接构造门，不必真玩 16 分）；
  - speedmath 打错 3 次验证 -2s 罚时真实生效（读计时条宽度）；
  - merge2048 合成 2048 后按键被忽略（`over=true` 锁）；
  - reaction 提前点击后本轮 +500ms 罚时真实计入。
- 落地位置：并入 vaccine-generators 或新建 `tests/state-machine-sweep.js`。

### P1-4 DOM+几何互证强制（对应盲区 C）
- 交互后的视觉关键元素必须断言 computed style（visibility/transform/背景/尺寸），
  截图只作 trace 不作断言。计算样式断言前统一 `style.transition='none'`（后台节流免疫）。
- 落地位置：sweep-2 升级时一并处理；工具函数 `assertVisible(el)` 入 GameKit 测试侧。

### P1-5 每游戏 DOM 形状契约（对应盲区 C 的静态面）
- 在 sweep-1 的 28 游戏签核里，为每款游戏声明" boot 后 DOM 形状"（子节点数量、必需子元素、
  网格轨道数）。dots 的 7 轨道 vs 49 节点、connect4 的 42 孔各含 1 个 `<i>`，这类契约
  一行断言就能锁死。已部分落地（V7）；**待办**：28 款全覆盖。

### P1-6 跨组件交互矩阵 + 泄漏不变量（对应盲区 D）
- 矩阵用例（每款游戏页执行）：
  1. 焦点在 `#searchInput` 时按 WASD/空格/方向键 → `defaultPrevented === false` 且输入完整（已落地 V8）；
  2. 语言切换 N=5 次后：`getEventListeners` 语义的监听器计数不变（测试侧用包装
     `addEventListener` 计数的探针实现）、`#stage` className 回到 `'stage'`、内存中无旧实例定时器存活
     （可用 monkey-patch `setTimeout/setInterval` 计数差值检测）；
  3. 收藏/最近玩过在 5 次语言切换后数据不丢。
- 落地位置：新建 `tests/cross-component-sweep.js`。

### P1-7 可玩性 oracle（对应盲区 E）
- 每款对抗/技巧类游戏配一个"作弊代理"冒烟：通过 `_test` 钩子读内部状态，
  在 ≤N 步内达成一次胜利（或失败路径），断言结算浮层出现且最佳分被写入。
  angles 的教训：**修好了 submit ≠ 能赢**。落地： angles 已人工验证（20° 命中），
  待办：tictactoe/connect4/dots（必胜策略存在）、runner/blocks/whack（可死也可活）。

### P2-8 对抗路径必测清单化（对应根因 5）
- 每游戏固定走一遍"故意输"路径：答错扣命、提前点击罚时、多付钱清空、踩雷结算——
  断言**罚则与文档一致**。部分已覆盖（lives 递减），补齐其余。

### P2-9 外部独立审查常态化（对应根因 3）
- 每次版本发布前跑一次 OCR 全量（`ocr review -c <commit> --exclude 'tests/**'`），
  结果进入与本报告相同的"四态定性 → 修复 → 疫苗"流程。经验：外部审查 8.9s 发现 24 处，
  是对"同作者盲区"最廉价的对冲。

### P2-10 漏斗表增加"断言强度"维度（对应根因 2）
- 测试报告的漏斗表按四类统计断言：存在性 / 状态等价 / 性质 / 端到端行为，
  并把"存在性占比"作为体系健康度红线（建议 < 40%）。当前 B-2 存在性占比约 70%，即为本次
  漏检的结构性信号。

## 五、给测试体系会话的执行顺序建议

1. 先把 P0-1 的性质检验从 4 款补到全部生成器类游戏（防最贵的 Critical 类复发）；
2. P0-2/P0-3 升级 B-2 断言强度与状态机覆盖（工作量最大，收益面最广）；
3. P1-4/P1-5/P1-6 并行；
4. P2 项按版本节奏带入；
5. 每项整改落地时，用本文第四节的映射表验证"该检查确实能抓住当年那个缺陷"
   （变异测试思路：把缺陷临时注回，断言必须变红）。

## 六、一句话结论

我们测的是"代码做了它做的事"，而没测"游戏是它声称的那个游戏"——
性质检验、状态深度、视觉契约、跨组件泄漏、可玩性这五个维度，
就是把前者升级为后者的清单。
